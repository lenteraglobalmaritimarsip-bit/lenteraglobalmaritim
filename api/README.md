# XAMPP API Setup

The PHP API connects to MariaDB with PDO. The local default database name matches the XAMPP database used in the setup (`maritim lgm`). For a different database or credentials, copy `config.local.example.php` to `config.local.php` and edit it. `config.local.php` is ignored by Git. Do not use the XAMPP `root` account or a blank password on a public server.

1. Import `database/schema.sql` into the application database to create the complete schema, including the PIC Name, Alamat, and No Tlp columns for Vendor Partners. For an existing database, apply the required SQL files in `database/migrations/`, including `20261020_add_inquiry_created_by.sql` to preserve the Inquiry creator's full display value. Apply `20261039_allow_shared_user_emails.sql` to an existing database to permit multiple users to share a corporate email; usernames remain unique and are the only supported login identifier. Existing migrations also add per-user drafts, notification read state, Account Payable payment details, separate EPDA/FDA ETA/ETD fields, global VAT options, stored payment proof images, yearly PDA/FPDA number sequences, autosaved PDA forms, Accounts Receivable entries with cash receipt photos, operational receipts without JOB/Vessel invoice references, legacy per-account cash-opening storage, the FDA-approved advance snapshot, and branch-scoped Finance. On a database that previously enabled Payment Voucher Error Correction, back up the database and apply `20261023_remove_payment_voucher_error_correction.sql` before deploying this release; it preserves actual payment records while deleting correction metadata and correction-specific audit logs. Before enabling AP payment currency locking on an existing database, apply `20261023_add_bank_account_currency.sql`; it classifies Mandiri account `1200055755990` as USD and Mandiri `1200055755883` plus BNI `2824121209` as IDR. Before enabling Admin cash balance adjustments on an existing database, apply `20261023_add_cash_balance_adjustments.sql`. Apply `20261024_add_branch_finance_scope.sql`, then `20261024_add_branch_master.sql`, to add company-branch ownership and stable branch IDs. The branch master is seeded with 001/JKT/Jakarta, 002/BJM/Banjarmasin, 003/SBY/Surabaya, 004/MKS/Makassar, 005/SRG/Semarang, and 006/BTM/Batam. Existing branch values matching these codes or names are mapped; unmatched values remain unassigned and must be corrected in Admin. Existing bank accounts are intentionally left unassigned if their owner branch cannot be inferred safely; set each account's **Branch Kantor (Pemilik Rekening)** in Admin > Bank Account before Finance can use it. If the snapshot migration has already been run, apply `20261022_classify_fda_receipts_by_approval.sql` once to classify FDA receipts using the recorded approval time and correct existing snapshots. Apply `20261023_add_login_lockout_and_audit.sql` once to enable account deactivation after three failed passwords and record authentication events. Current cash-opening amounts are defined in the application release and are not edited through this storage table.
   On an older database also apply `database/migrations/20261016_cleanup_unused_schema.sql` (drops unused tables/columns; MariaDB 10.5+).
2. From the project root, create the first administrator. The generated password is printed once; save it securely.

```powershell
C:\xampp\php\php.exe api\create_admin.php
```

If the one-time password was lost, reset it from the project root with `C:\xampp\php\php.exe api\reset_admin_password.php`. This generates and prints a new password once; it does not expose or recover the old password.

3. Start the Vite app and PHP API together from the project root:

```powershell
npm run dev
```

On Windows, the dev server automatically detects PHP installed under Laragon or XAMPP. Otherwise, put `php` on `PATH` or set `PHP_EXECUTABLE` to the PHP executable path. The Vite dev server proxies `/api` to PHP at `localhost:8000`.

4. Set `VITE_API_AUTH_ENABLED=true` in the ignored `.env.local` file and restart Vite. API mode is required; the application does not persist data in browser storage or fall back to local storage when the API is unavailable.
5. Sign in using the generated admin account. On an empty database, the first admin session seeds the app's initial master data. Add real role accounts in Admin > Users; demo password presets are hidden in API mode.

The API uses `HttpOnly` PHP sessions, CSRF tokens, password hashes, PDO prepared statements, and a configurable allowed origin. Use HTTPS outside localhost.

The app state maps to relational tables in a transaction. Root master and Job records are upserted rather than deleted and reinserted, so foreign-key cascades cannot remove durable PDA/FPDA documents during state synchronization. User-specific drafts and notification read state are stored in `user_app_data`, keyed to the authenticated user. The API uses an HttpOnly session cookie; the browser retains only that session cookie, not application data. The adapter is intended for local workflow testing with one active browser session. Before multi-user/public deployment, replace whole-state synchronization with revision-checked incremental writes and enforce per-workflow permissions server-side.

Document numbering is branch-scoped: Job and Inquiry numbers include the branch code; EPDA and FDA number series are separate per branch and year; PDA and FPDA use separate database sequences per branch and year. Finance payment requests and vouchers use `OPS{BRANCH}-####-MMYY` and `PV{BRANCH}-####-MMYY`, respectively. The existing Manager OPS job approval remains one approval per job and is restricted to the job's branch. PDA/FPDA drafts and approvals are also limited to their owning branch. Cash balances, Finance journal/recap, bank-account choices, and Accounts Receivable history are scoped to the authenticated Finance branch. A bank account belongs to one company branch; the bank's own physical branch remains a separate field.

Branch IDs are generated automatically by the database and displayed with three digits (001, 002, ...); branch codes are used in document numbers and branch names are display labels. Never delete a branch or renumber its ID. To add a branch, insert its unique uppercase code and name into `branches` without supplying an ID, using a reviewed migration (for example `INSERT INTO branches (code, name) VALUES ('PTK', 'Pontianak');`); the database assigns the next ID and the branch appears in the Admin selectors. Do not edit branch codes already present on historical documents without an explicit data migration. Branch rows are not editable through whole-state application saves.

PDA numbers and autosaved PDA drafts are managed by `api/pda.php` using the authenticated user's branch and the `Asia/Jakarta` calendar year/month. Sales PDA numbers use the format `0001/PDA-LGM-BRANCH/MM/YYYY`, starting at `0001` for each branch and year; EPDA must exist before a Sales PDA can be opened. FPDA numbers use a separate sequence in the format `0001/FPDA-LGM-BRANCH/MM/YYYY`, also starting at `0001` for each branch and year. Autosave updates the existing document revision and does not allocate a new number. Header fields, item rows, and the in-progress item form are stored in the `pda_documents` and `pda_items` tables, with revision checks to prevent silent overwrites between sessions. FDA users can continue items from the same Job's Sales PDA; copied item details are appended and source-to-FPDA item references are autosaved to avoid repeated imports.

Finance COA master: retain the `chart_of_accounts` table and existing COA rows for Admin > Master Data > Chart of Accounts. On an existing database without the COA master, apply `database/migrations/20261025_add_finance_coa.sql` after the branch Finance and branch master migrations. On a fresh install, import `database/schema.sql`, then `database/seeds/20261025_chart_of_accounts.sql`. Finance AP/AR does not require bank-account COA mapping or journal lines. To enable central Accounting, apply `20261029_add_accounting_role_and_journals.sql`, then `20261030_add_receivable_voucher_numbers.sql`, then `20261031_add_accounting_assets.sql` after the branch and COA master migrations. This last migration creates the Accounting asset register and imports 48 legacy assets from the supplied reference SQL with Jakarta/Banjarmasin branch mapping. Accounting has no assigned branch; its protected endpoints read transactions and assets across all branches. Jurnal sources remain separate and immutable after posting; asset depreciation is an estimate only and does not create journals automatically. New AR receipts receive an independent `RV{BRANCH}-{SEQUENCE}-{MMYY}` number; existing entries remain nullable and unchanged. Migrations `20261026_add_receivable_coa.sql`, `20261027_add_finance_journal_lines.sql`, and `20261028_add_finance_journal_numbers.sql` are not prerequisites for Finance AP/AR. If those earlier migrations were already applied, leave their data in place; do not drop COA or history.

Payment Voucher PPh rates: on an existing database, back up the database and apply `database/migrations/20261033_add_payment_voucher_pph_rate.sql` before deploying the updated API/frontend. It adds the selected rate while preserving old vouchers (existing PPh deductions are migrated as 2%). Fresh installs get the column from `database/schema.sql`.

Payment Voucher ePDA detail fields: before deploying the updated API/frontend to an existing database, back up the database and apply `database/migrations/20261035_add_payment_voucher_epda_fields.sql` and `database/migrations/20261036_add_payment_voucher_tariff_type.sql`. Existing voucher rows keep their amount with `price = amount` and `quantity = 1`. Fresh installs get these columns from `database/schema.sql`.

The Accounting `Rincian Laba` report uses `GET /api/accounting.php?action=profit-loss-monthly&year=YYYY&scope=ALL` (or `scope=BRANCH&branchId=...` / `scope=HISTORICAL`) to aggregate posted journals by account and month in one query. This report adds no database tables or migrations.

The central `DIRECTOR` role is read-only across branches and can view financial summaries, assets, posted journals, vessel calls, and recent activity logs. On an existing database, apply `database/migrations/20261034_add_director_role.sql` before assigning the role. The application-state API rejects Director writes; Accounting journal and asset mutation endpoints remain exclusive to `ACCOUNTING`.
